    스킬 시스템

    ScriptableObject로 스킬을 데이터로 분리해, 코드 수정 없이 스킬 추가와 밸런스 조정이 가능합니다.

    예시 · 스나이퍼 스킬

    • Lv.1 Q 키 → 적을 관통하는 총알 발사
    • Lv.2 성장 시 강력한 한 발 (스나이퍼 모드)

    맵 시스템

    층마다 미리 만든 맵 중 하나를 무작위로 불러오고, 몬스터를 모두 처치하면 다음 층 문이 열립니다.

    구조를 바꾼 이유

    처음에는 20개 층을 하나씩 손으로 만들 계획이었지만, 일정과 아이디어가 부족해진다는 기획자의 제안을 받아 미리 만든 맵을 무작위로 불러오는 방식으로 바꿨습니다.

    한 층이 진행되는 순서

    1. 맵 생성1~9층은 맵 목록에서 무작위 선택, 10층은 보스 맵
    2. 길 찾기 준비맵이 만들어진 뒤 몬스터 이동 경로(NavMesh)를 계산
    3. 몬스터 배치스폰 위치마다 몬스터 종류를 무작위로 골라 배치
    4. 클리어 판정몬스터를 모두 처치하면 보상과 함께 다음 층 문이 열림

    데이터 설계 & 최적화

    함께 일하는 기획자와, 무거운 전투 구간을 위해 만든 구조

    JSON 데이터 분리

    몬스터 능력치를 코드에 하드코딩하지 않고 JSON으로 분리했습니다. 기획자가 코드 수정 없이 밸런스를 조절할 수 있는 구조입니다.

    오브젝트 풀링

    트러블슈팅 — 인벤토리 능력치 연결 버그

    문제
    장비를 장착해도 공격력·이동속도가 오르지 않음. 다른 팀원이 만들던 인벤토리를 넘겨받은 상태라 원인이 한눈에 보이지 않음.
    원인
    장비 능력치를 캐릭터가 읽지 않는 attackScript(인벤토리 공격력)에 저장하고 있었음.
    해결
    캐릭터가 실제로 읽는 playerScript 변수에 '인벤토리 공격력 + 플레이어 공격력' 최종값을 전달하도록 수정.

    핵심 버그는 계산이 아니라 '어디에 저장하느냐'의 문제. 남의 코드도 끝까지 추적해 원인을 찾았습니다.

    출시 후 유저 피드백 반영

    출시로 끝내지 않고, 커뮤니티에 남은 피드백을 받아 게임을 다듬었습니다.

    • “대쉬 쿨타임이 작아 안 보인다”

      → 쿨타임을 캐릭터 옆 UI로 시각화

    • “충돌 판정이 넉넉해 길막당한다”

      → 오브젝트 충돌 판정 범위 조정

    배운 점 만드는 사람은 놓치지만, 플레이하는 사람은 바로 느끼는 지점이 있다는 것을 배웠습니다.

    고발 시스템

    딜러의 속임수를 눈치채고 고발해 승패를 뒤집는 심리전 장치

    1. 딜러가 카드를 조작라운드 진행 중 딜러는 몰래 카드를 바꿀 수 있다
    2. 패배한 플레이어가 고발진 쪽이 딜러의 조작을 의심하면 고발을 선택
    3. 고발 판정조작이 있었으면 고발 성공, 없었으면 실패
    4. 승패 역전 또는 유지성공 시 결과가 뒤집히고, 실패 시 그대로 패배

    내가 구현한 부분

    • 카드 게임의 규칙과 고발 로직 구현
    • 고발 성공·실패에 따라 승패 결과를 전환하는 처리
    • Photon으로 여러 플레이어가 같은 게임 상태를 공유하도록 동기화

    Photon 멀티플레이

    한 사람의 행동이 다른 사람 화면에도 똑같이 반영되도록 게임 상태를 맞췄습니다.

    플레이어 1 플레이어 2 플레이어 3 ↕↕↕ 공유되는 게임 상태 각 플레이어의 행동 ↔ 게임 상태 실시간 공유

    내가 맡은 부분

    • 게임 방을 만들고 입장하는 기능
    • 카드 분배·턴 진행 같은 상태를 플레이어끼리 맞추기
    • 한 명의 행동이 다른 화면에도 반영되도록 동기화

    트러블슈팅 — GameDirector 리팩터링

    문제
    게임 진행 로직과 화면 표시(UI) 코드가 GameDirector 한 클래스에 몰려, 인스펙터에서 값을 찾고 수정하기가 점점 어려워짐.
    원인
    게임 규칙 처리와 칩·머니바·승패 표시 같은 UI 갱신이 한 클래스에 섞여 책임이 과도하게 집중됨. 하드코딩된 값도 관리가 힘들어짐.
    해결
    화면 표시 코드를 역할별로 4개 클래스(Presenter 1개 · View 3개)로 분리하고, 하드코딩을 걷어냄.
    결과
    기능별 위치가 명확해져 값 수정과 디버깅이 쉬워짐. '동작하는 코드'와 '유지보수되는 코드'의 차이를 체감.

    Before

    GameDirector게임 진행 + 화면 표시가 한 클래스에 ↓ 화면 표시 코드를 역할별로 분리

    After

    GamePanelPresenter핫시트·네트워크 공통 화면 조작 BetChipsView판돈 칩·금액 표시 MoneyBarView플레이어별 머니바 ResultMarkerView승패 표식 (왕관·비석)

    게임 진행은 GameDirector에 남기고, 화면 표시만 4개 클래스로 분리
